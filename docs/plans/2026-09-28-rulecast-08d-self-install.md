# rulecast Plan 8d — rulecast on rulecast

> **For agentic workers:** Use the executing-plans skill to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** rulecast delivers its own conventions to the agents editing it. The repository gets a `.rulecast-config.yaml` with catalog rules and rules drafted from its own spec, hooks installed for Claude Code, and a written record of what `init` got wrong on a TypeScript monorepo — the shape the 2026-09-22 trial never covered.

**Approach:** Run the real flow, unmodified, as a user would: `rulecast init --agent claude-code`, then `agents/DRAFT-RULES.md` against the spec and 200-odd commits of conventions. Every place the flow stumbles is a defect in rulecast, fixed here rather than worked around. The repository is expected to be *clean* on its own conventions, so this is the wrong place to measure enforcement and the right place to check whether staying compliant is free.

**Stack:** the shipped CLI, run against this repository.

Prerequisite: plan 7 is done. Best after `08c` — `rulecast test` is what turns drafted rules from guesses into measured ones — but it does not require it.

---

## Why

pre-commit runs pre-commit on itself. A tool whose thesis is *"your agent read your conventions forty tool calls ago"* that does not deliver its own conventions to the agents editing it is a gap a reviewer notices in the first minute — and agents work this repository constantly. Grepping the specs and plans, self-installation was never considered.

It also road-tests `init` on a shape it has never seen. The 2026-09-22 trial was a FastAPI + React application; this is a pnpm workspace of four packages with no application code, where the rule packages are data and the CLI is the product.

## Decisions this plan implements

1. **The flow is run as written, not as the author knows it works.** Anything that needs a flag `agents/SETUP.md` does not mention, or a step the drafting prompt does not describe, is a defect in the documents. Note it, fix the document, and re-run from the top.

2. **Hooks are installed in `.claude/settings.json`, the shared scope, and that is the user's call.** It changes every Claude Code session in this repository, including the user's own. Task 3 does not run until they have said yes to what it will write. `rulecast install`/`uninstall` manage the file; nothing edits it by hand (`agents/SETUP.md`, Never).

3. **Rules are drafted from the spec, not invented.** `docs/specs/2026-09-15-rulecast-design.md` is 845 lines of stated conventions and the plans carry more. A rule that cannot be traced to a sentence somewhere in `docs/` does not go in the config.

4. **Expect it to be clean, and say so if it is.** A self-install that reports zero violations is the correct result and is worth writing down: it means compliance is free here. What it cannot tell us is whether enforcement works, and this document must not be read as evidence that it does.

5. **`docs/evidence/` is not renamed in this plan.** `docs/evidence/` was agreed and then deliberately reverted, so the rename is undone rather than rejected. **Ask before renaming**, and do it as its own commit if the answer is yes.

## Candidate conventions, from the repository's own documents

Drafting decides the final list; these are where to look, each traceable to a document:

| Convention | Source | Likely shape |
|---|---|---|
| No module-level mutable state in `src/`, except `src/detectors/ast-grep/load.ts` | plan index, Conventions | `ast-grep`, with the one file excluded |
| No test may call a model or open a socket to one | spec §15 | `regex` over `test/`, plus `context` pointing at §15 |
| Tests never touch the real cache; use `test/helpers/home.ts` | plan 7a, Conventions | `regex` or `ast-grep` over `test/` |
| A detector reads only through `run`'s `read`, never from disk | spec §6, Contract | `ast-grep` on `node:fs` imports under `src/detectors/` |
| `src/` never imports from `test/` | implicit, worth stating | `regex` |
| Every rule key change touches the spec, the agent reference and the manifest generator together | plans, repeatedly | `touch` rule delivering §4 |
| Detector contract suite runs for every built-in detector | spec §15 | `touch` rule on `src/detectors/` |

The catalog's `generated-code` rule applies as-is: `.rulecast-rules.yaml` is generated by `pnpm manifest` and says so on line 1.

## Conventions

As plan 8a, with two differences:

- **`init` and `install` write outside `packages/`.** Review every file they touch before committing, by exact path.
- Commit the configuration separately from any rulecast defect this turns up, so the defect fix is reviewable on its own.

## Open

**Task 3's last verification, and end-to-end step 4, were never done.** Both ask for a delivery
observed inside a real Claude Code session. What was actually done is `rulecast hook claude-code`
driven directly with the recorded payload shapes from `packages/rulecast/test/payloads/claude-code/`,
confirming the session state it writes and the latency it costs — the whole mechanism except Claude
Code doing the invoking. That is worth something, and it is not what the box claimed.

The gap is narrow but it is the only part nothing else covers: that Claude Code's hook configuration
in `.claude/settings.json` actually fires the command, with the payload the fixtures were recorded
from, in a session nobody instrumented. The fixtures pin the parse; the hooks firing at all is the
untested half.
