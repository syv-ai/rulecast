# Dogfooding rulecast on aka-agents2

**Date:** 2026-09-22 · **Target:** a private FastAPI + React platform, 1,945 tracked files (854 `.py`, 444 `.tsx`, 401 `.ts`), at its `v1.98.0` release commit · **rulecast:** the 0.1 candidate, built from source

Spec §15 lists dogfooding as a test, and it is the only item in 0.1 that could still say the design is wrong. This is what it said.

**Everything ran on a throwaway `git clone --local` of the target.** Its own checkout was never written to: `git status --short` and `git worktree list` were identical before and after.

## What was exercised

| Step | Result |
|---|---|
| `rulecast doctor` with no config | The "no `.rulecast-config.yaml` … (run rulecast init)" error, exit 2. Correct. |
| `rulecast init --yes --agent claude-code` | Detected `python · typescript · javascript · react · CLAUDE.md · 52 other docs · Claude Code`. Wrote the config and 6 hooks, selected 8 catalog rules, validated, printed the drafting prompt. Exit 0. |
| `rulecast doctor` on the configured project | 120 ms. All 8 rules dry-run, environment and hooks clean. |
| `rulecast run --all-files` | **1,945 files in 1.27 s**, 168 findings, 0 warnings, 0 errors. |
| Drafting 3 local rules from `CLAUDE.md` | Followed `agents/DRAFT-RULES.md`. 11 rules valid. |
| One `llm` rule, run for real | 6 findings across 3 dialogs, each naming a specific close path. |

The standalone-`CLAUDE.md`-with-no-`AGENTS.md` case — one of the doc cases `init` handles explicitly (spec §12) — had only ever been tested against a fixture. It worked on the real thing.

| `generated-code` | 16 | True. Catches `*.gen.*` — but see below. |

**131 findings from one rule is the case `DRAFT-RULES.md` exists to surface** — it tells the agent to report existing matches and ask the developer to keep, edit or drop each rule. That flow worked: the number made the decision obvious. It is a catalog-tuning question, not a rulecast defect.

## What drafting added over the catalog

The project's `CLAUDE.md` says "DO NOT EDIT `src/client/`". The catalog's `generated-code` rule matches `*.gen.*` and `__generated__/`, which is **15 of the 17 files** in that directory. A local `path` rule over `^frontend/src/client/` catches all 17. That is the drafting step earning its place: the catalog gets you most of the way, and the project's own words close the gap.

Three of spec §15's four named conventions turned out to be covered by catalog rules already — unsurprising, since plan 4a drew the starter catalog from this project's conventions. The fourth is the interesting one.

## The `llm` rule

`useUnsavedWork` on close paths is the convention nothing mechanical expresses: "a surface holding unsaved user input declares it with `useUnsavedWork`, and every close path awaits `confirmClose()`". A `regex` or `ast-grep` rule cannot decide what "holding unsaved user input" means.

Drafted as an `llm` rule over `components/**/*(Dialog|Drawer).tsx`, `model: haiku`, run for real against 7 dialogs. It found 6 issues, each naming a close handler and the state that would be lost — for example a dialog whose Cancel button and close button both discard form data without the hook, and one whose rich-text editor content is dropped on close. They read like findings a reviewer would make.

**This is the strongest evidence in the exercise that the `llm` detector's design is right.**

## Defects found and fixed

1. **A multi-line match corrupted the message.** 131 of 168 findings had a newline in the middle of the message: an ast-grep rule matching `style={{ … }}` across several lines put those lines straight into `{{text}}`, and every renderer — terminal, agent, json, sarif — assumes one finding is one line. Fixed in `renderTemplate`, so there is one place it can be got wrong; an `llm` rule's `{{reason}}` has the same shape and is fixed by the same change. Verified: same 168 findings, 0 messages containing a newline.

2. **A timeout that told you nothing.** A single `claude -p --model haiku` call on a 135-line file measured **89 s** against the default `verify_ms` of 60 s, and the warning said only "llm detector timed out for local/unsaved-work". It now names the timeout that was exceeded and the setting to raise. Spec §14's verify-timeout behaviour also had no test; it has two now.

3. **`doctor` mislabelled a resolving alias.** It reported `model "haiku" — passed through` for the `claude-code` provider, because `haiku` resolves to itself there. "Passed through" is only true of a name that is not an alias, and saying it of one reads as "rulecast does not know this model". Now: `claude-code calls it haiku`.

## Open question for the user

**Should `timeouts.verify_ms` default higher than 60 s?** Measured here: one `haiku` call on a 135-line file took 89 s; four concurrent calls took 32 s in total; a 4 KB file took 10 s. The variance is wide and the tail exceeds the default. The catalog itself ships an `llm` rule (`python/thin-routes`), so a project that enables it with default settings can hit this.

Raising it changes how long an agent's Stop may block — the Claude Code Stop hook timeout is `verify_ms + 10 s` (spec §12) — so it is a product decision, not a bug fix. The options are: leave 60 s and document that `llm` rules need it raised; raise the default to ~120–180 s; or give `llm` its own timeout separate from the rest of a verify.

## Would a developer on this project keep these rules on?

**The Python rules and the drafted local rules, yes.** `python/no-queries-in-services` (11), `python/no-silent-except` (9) and `local/no-client-edits` (17) are all true positives against conventions the project wrote down itself, at a volume a team would actually work through.

**`react/no-inline-style`, no** — and the drafting flow made that obvious in one command rather than after a week of noise.

**The `llm` rule, yes, with its timeout raised.** It found six real problems no other detector in rulecast could have found, for about a cent a file.
